1. CORE MEMORY PARAMETERS & FORMULAS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

┌─────────────────────────────────────────────────────────────────────────────┐
│ ALL OPERATING SYSTEMS (Windows, Linux, UNIX)                                │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│ PHYS_MEMSIZE                                                                │
│ └─ Definition: Size of main memory (RAM) in GB                             │
│ └─ Formula: = Available Physical Memory (after deducting DB/other apps)    │
│ └─ Example: PHYS_MEMSIZE = 256 (for 256 GB system)                         │
│ └─ Reference: SAP Note 88416, 941735, 2085980                              │
│                                                                              │
│ em/initial_size_MB                                                          │
│ └─ Definition: Initial Extended Memory pool at startup                      │
│ └─ Formula: = min(512000, PHYS_MEMSIZE_GB × 1024 × 0.7)                    │
│ └─ Example: min(512000, 256 × 1024 × 0.7) = 184320 MB                      │
│ └─ Impact: TOO LOW → ROLL_FULL errors, work process termination           │
│ └─ Impact: TOO HIGH → Startup failures, memory exhaustion                  │
│                                                                              │
│ em/max_size_MB                                                              │
│ └─ Definition: Maximum limit for EM extension                              │
│ └─ Formula: = PHYS_MEMSIZE_GB × 1024 × 0.9                                │
│ └─ Example: 256 × 1024 × 0.9 = 235520 MB                                   │
│ └─ Note: Provides headroom for EM growth above initial_size                 │
│                                                                              │
│ EM/TOTAL_SIZE_MB                                                            │
│ └─ Definition: Total EM pool size (introduced Kernel 7.40)                 │
│ └─ Formula: = PHYS_MEMSIZE_GB × 1024 × 0.7                                │
│ └─ Example: 256 × 1024 × 0.7 = 184320 MB                                   │
│ └─ Note: Acts as soft limit for user context memory                        │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│ WINDOWS SERVER SPECIFIC PARAMETERS (SAP Note 88416)                         │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│ Pagefile Size (CRITICAL)                                                    │
│ └─ Formula: = PHYS_MEMSIZE × 2 (MUST be FIXED size, not dynamic)          │
│ └─ Example: 256 GB RAM → Pagefile 512 GB (fixed)                           │
│ └─ Configuration: Windows System → Advanced → Virtual Memory               │
│ └─ TOO SMALL: Error 1455 "Paging file too small" → System crash           │
│ └─ TOO LARGE: Disk space waste (but safer than too small)                  │
│ └─ MUST NOT USE: "System Managed" pagefile (it's dynamic)                  │
│                                                                              │
│ abap/heaplimit                                                              │
│ └─ Definition: Max memory per work process                                  │
│ └─ Formula: = PHYS_MEMSIZE_GB × 1024 / (Dialog_WPs)                       │
│ └─ Example: 256 × 1024 / 30 = 8704 MB per WP                               │
│ └─ Note: Used only for sanity check, not for ZAMM calculation             │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│ LINUX/UNIX SPECIFIC PARAMETERS (SAP Note 941735, 3681846)                   │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                              │
│ es/implementation (CRITICAL on Linux)                                       │
│ └─ Value for 64-bit: std (STD implementation)                              │
│ └─ Legacy for 32-bit: map (MAP implementation - DEPRECATED)                │
│ └─ Default (K7.10+): std on 64-bit systems                                 │
│ └─ Impact: Controls memory addressing model and shared memory behavior     │
│ └─ Reference: SAP Note 941735                                              │
│                                                                              │
│ em/blocksize_KB                                                             │
│ └─ Definition: Memory block allocation granularity                          │
│ └─ Value: 4096 KB (standard for all)                                       │
│ └─ Note: Fixed value, auto-set by SAP                                      │
│                                                                              │
│ em/global_area_MB                                                           │
│ └─ Definition: Global shared data area                                      │
│ └─ Formula: = EM_TOTAL_SIZE_MB × 0.15                                      │
│ └─ Example: 184320 × 0.15 = 27648 MB                                       │
│                                                                              │
│ abap/shared_objects_size_MB                                                 │
│ └─ Definition: Shared program & table storage                              │
│ └─ Formula: = EM_TOTAL_SIZE_MB × 0.1                                       │
│ └─ Example: 184320 × 0.1 = 18432 MB                                        │
│                                                                              │
└─────────────────────────────────────────────────────────────────────────────┘

  Database              = None
  Other Apps            = None
  Available for SAP     = 256 GB
  Kernel                = 7.40+

Calculations:
  PHYS_MEMSIZE          = 256 GB
  em/initial_size_MB    = min(512000, 256 × 1024 × 0.7) = 184320 MB
  em/max_size_MB        = 256 × 1024 × 0.9 = 235520 MB
  EM/TOTAL_SIZE_MB      = 256 × 1024 × 0.7 = 184320 MB
  Pagefile_Size         = 256 × 2 = 512 GB (FIXED)
  abap/heaplimit        = (256 × 1024) / 30 = 8704 MB

Profile Parameters:
  PHYS_MEMSIZE = 256
  em/initial_size_MB = 184320
  em/max_size_MB = 235520
  EM/TOTAL_SIZE_MB = 184320

System Actions:
  ✓ ZAMM enabled automatically
  ✓ All parameters auto-derived from PHYS_MEMSIZE
  ✓ Set Windows pagefile to 512 GB (fixed, not dynamic)
  ✓ No manual memory parameter tuning needed

PROBLEM: Application Server Won't Start
─────────────────────────────────────────

Symptoms:
  • "Cannot allocate memory" during startup
  • Process hangs at initialization
  • /var/log/messages shows allocation failures

Root Cause Analysis:
  1. em/initial_size_MB too large → exceeds available physical RAM
  2. Pagefile/swap too small on Windows/Linux
  3. System out of memory or fragmented
  4. Other processes consuming memory

Solution Steps:
  1. Reduce em/initial_size_MB by 10-20%
     OLD: 184320 MB → NEW: 160000 MB
  2. Increase Windows pagefile (add more space)
  3. On Linux: increase swap space
  4. Reduce em/max_size_MB if needed
  5. Restart application server
  6. Monitor startup logs (SM21, dev_disp)
  7. Once running, gradually increase to calculated values

Recovery Profile:
  PHYS_MEMSIZE = 256 (unchanged)
  em/initial_size_MB = 160000 (reduced from 184320)
  em/max_size_MB = 200000 (reduced from 235520)
  em/blocksize_KB = 4096 (unchanged)


PROBLEM: "ROLL_FULL" Errors in Work Processes
───────────────────────────────────────────────

Symptoms:
  • Work processes terminate unexpectedly
  • SM21 shows "ROLL_FULL" message
  • Users report session disconnects
  • Batch jobs fail mid-execution

Root Cause Analysis:
  1. em/initial_size_MB too low (TOO SMALL pool)
  2. EM/TOTAL_SIZE_MB not calculated correctly
  3. em/max_size_MB too restrictive
  4. ABAP program using excessive memory

Solution Steps:
  1. Check current calculated value vs. profile
  2. Increase em/initial_size_MB to calculated value
     Example: 150000 MB → 184320 MB
  3. Increase em/max_size_MB (add buffer)
     Example: 200000 MB → 235520 MB
  4. Check abap/heaplimit (per-process limit)
  5. Identify memory-heavy programs in SM21
  6. Plan restart with adequate free physical RAM
  7. Verify pagefile/swap is adequate
  8. Perform controlled restart

After Restart:
  • Monitor ST06 (memory tab) continuously
  • Check SM04 (work processes) for errors
  • Run test batch jobs
  • Wait 48 hours to confirm stability


PROBLEM: Pagefile Too Small (Windows Only)
───────────────────────────────────────────

Symptoms:
  • Error 1455: "Paging file is too small for this operation"
  • System becomes unresponsive or crashes
  • Cannot execute large reports
  • All work processes terminate simultaneously

Root Cause Analysis (Windows):
  1. Pagefile size < 2 × physical RAM
  2. Pagefile set to "system managed" (dynamic)
  3. Application server tries to exceed available memory

Solution Steps (MUST be done BEFORE restart):
  1. Calculate required pagefile: 2 × PHYS_MEMSIZE GB
     Example: 2 × 256 GB = 512 GB
  2. Open Windows System Properties
     → Advanced → Virtual Memory → Change
  3. Uncheck "Automatically manage paging file"
  4. Set FIXED size (NOT range):
     Initial Size: 512000 MB
     Maximum Size: 512000 MB (same as initial - FIXED)
  5. Click "Set" then "OK"
  6. May require reboot of Windows server
  7. Restart application server after Windows reboot

Verification:
  • Open Event Viewer → System
  • Look for Virtual Memory warnings
  • Confirm pagefile size with: fsutil volume querycluster C: /free


PROBLEM: System Very Slow / Excessive Swapping
────────────────────────────────────────────────

Symptoms (Linux):
  • CPU utilization high but work processes not busy
  • vmstat shows si/so (swap in/out) increasing
  • System feels sluggish, reports timeout
  • ST06 shows "Physical memory critical"

Symptoms (Windows):
  • Disk I/O high (pagefile reads/writes)
  • Performance monitor shows "% Disk Time" > 50%
  • High page faults in perfmon

Root Cause Analysis:
  1. em/initial_size_MB too large for physical RAM
  2. Insufficient swap/pagefile configured
  3. Memory fragmentation
  4. Other processes running on same host

Solution Steps:
  1. Reduce em/initial_size_MB by 20-30%:
     OLD: 184320 MB → NEW: 140000 MB
  2. Verify adequate swap/pagefile:
     Linux: free -h | grep Swap (minimum 10-20 GB)
     Windows: dfrag.exe → Pagefile size
  3. Check for memory-hungry processes:
     Linux: top -o %MEM
     Windows: Task Manager → Memory tab
  4. Plan restart during low-usage window
  5. After restart, monitor for 2 hours:
     - Linux: watch free -h (every 5 seconds)
     - Windows: perfmon → Memory counters
  6. Gradually increase em/initial_size_MB back to calculated

Prevention:
  • Monitor memory daily with ST06/ST07
  • Set alerts when memory > 80% utilized
  • Review memory sizing annually
  • Use this calculator tool before each parameter change


PROBLEM: Parameter Discrepancies After Profile Upload
───────────────────────────────────────────────────────

Symptoms:
  • Calculated values much higher than current profile
  • Calculated values much lower than current profile
  • Warnings shown in comparison table

Resolution for HIGHER Calculated Values:
  Likely Cause:
    • Profile created on smaller hardware
    • System migrated to larger VM, profile not updated
    • Conservative sizing was intentional

  Decision Points:
    1. Why are current values lower? (documented in profile?)
    2. Is there a business reason for conservative sizing?
    3. Available physical memory usage (run ST06)?
    4. Do users/reports complain of memory issues?

  Action Plan:
    • If memory available: gradually increase to calculated
    • If business reason: document why and override
    • If uncertain: contact system owner or SAP team
    • Apply changes with planned downtime

Resolution for LOWER Calculated Values:
  Likely Cause:
    • Profile created for different-sized hardware
    • Manual increases made over time without review
    • Calculated values may be conservative

  Investigation:
    1. When was profile last reviewed?
    2. Was there a specific reason for higher values?
    3. Performance issue history on this system?
    4. Actual physical RAM vs. profile assumption

  Action Plan:
    • Use larger of (calculated, current) if well-documented
    • Apply calculated if previous values arbitrary
    • Test with calculated values in QA first
    • Document decision with timestamp

6. IMPACT ANALYSIS: COMMON WRONG CONFIGURATIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

MISCONFIGURATION #1: PHYS_MEMSIZE Not Set or Wrong
───────────────────────────────────────────────────

Example:
  System has 256 GB RAM but PHYS_MEMSIZE = 128 GB (or missing)

Impacts:
  ❌ ZAMM doesn't function (no base value to calculate from)
  ❌ em/initial_size_MB remains at old/default (too low or too high)
  ❌ System doesn't scale memory with available resources
  ❌ Manual parameter tuning becomes necessary
  ❌ New hardware deployments don't auto-configure memory

Recovery:
  ✓ Set PHYS_MEMSIZE = actual available RAM (minus DB reservations)
  ✓ Remove all other em/* parameters (let ZAMM recalculate)
  ✓ Restart application server
  ✓ ZAMM automatically adjusts all memory settings


MISCONFIGURATION #2: em/initial_size_MB Too Low
────────────────────────────────────────────────

Example:
  System calculated = 184320 MB, but profile has em/initial_size_MB = 100000

User Experience:
  Week 1: ✓ System runs fine
  Week 2: ⚠ Occasional user timeouts
  Week 3: ❌ Frequent "ROLL_FULL" errors
  Week 4: 🔴 Work processes crash after 10-15 minutes

Business Impact:
  • Loss of productivity (users disconnected)
  • Batch jobs failing (month-end closing delayed)
  • Escalations to support team
  • Potential data consistency issues if ABAP not saved

System Logs:
  SM21 (System Logs):
    ROLE|0 : ROLL_FULL, W8/WM_ATTACH_ROLL_FAILED
  dev_disp:
    Memory allocation error, EM pool exhausted
  SLDCHECK:
    Memory pressure alerts

Fix Required:
  1. Increase em/initial_size_MB → 184320
  2. Increase em/max_size_MB → 235520
  3. Increase EM/TOTAL_SIZE_MB → 184320
  4. Verify pagefile/swap ≥ 2× RAM
  5. Restart during maintenance window
  6. Monitor for 48+ hours after restart


MISCONFIGURATION #3: em/initial_size_MB Too High
──────────────────────────────────────────────────

Example:
  System has 256 GB RAM, but em/initial_size_MB = 400000 MB (unrealistic)

Symptoms at Startup:
  ❌ Application server fails to start
  ❌ "Cannot allocate 400 GB" error message
  ❌ disp+work process crashes immediately
  ❌ Entire business operations unavailable

Duration of Outage:
  • Time to diagnosis: 15-30 minutes
  • Time to fix and restart: 10-20 minutes
  • Total downtime: 30-60 minutes
  • Business impact: Critical (system unavailable)

Recovery:
  1. Reduce em/initial_size_MB to calculated value: 184320
  2. Reduce em/max_size_MB to: 235520
  3. Restart application server
  4. Monitor application logs for success
  5. Gradually increase if needed (don't just guess)

Prevention:
  • Use ZAMM calculator to validate all parameter changes
  • Never manually increase em/initial_size_MB > calculated
  • Test changes in non-production first
  • Have rollback plan (previous profile backed up)


MISCONFIGURATION #4: Windows Pagefile = Dynamic (System Managed)
────────────────────────────────────────────────────────────────

Example:
  Pagefile configuration: "System managed" OR Initial=512 MB, Max=2048 MB

Symptoms:
  Week 1: ✓ Everything works
  Week 2-3: ⚠ Occasional slowness
  Week 4: 🔴 Error 1455: "Paging file is too small for this operation"
           Application Server CRASHES

Impact:
  • Entire system becomes inaccessible
  • All users disconnected
  • No graceful degradation (immediate crash)
  • May cause database issues if transactions mid-flight
  • Recovery time: 30 minutes to 2 hours (emergency restart)

Why This Happens:
  • Dynamic pagefile tries to grow but CAN'T grow fast enough
  • As EM needs extend, pagefile can't allocate quickly
  • SAP requires FIXED pagefile for predictable performance
  • Dynamic pagefile was designed for office applications, not SAP

Correct Configuration (Windows):
  1. System Properties → Advanced → Virtual Memory → Change
  2. UNCHECK "Automatically manage paging file"
  3. Select drive with most free space
  4. Set Initial Size: 512000 MB (512 GB for 256 GB RAM example)
  5. Set Maximum Size: 512000 MB (SAME VALUE = FIXED)
  6. Click "Set" then OK
  7. Reboot Windows server
  8. Verify: dfrag.exe shows pagefile 512 GB

Reference: SAP Note 1518419 - Pagefile MUST be fixed size


MISCONFIGURATION #5: No Account for Co-located Database Memory
──────────────────────────────────────────────────────────────

Example:
  System has 512 GB RAM total, but:
  • SAP HANA database needs 300 GB
  • Profile set PHYS_MEMSIZE = 512 (didn't subtract!)
  • Calculated em/initial_size_MB = 350+ GB
  • Result: BOTH SAP and HANA compete for memory → BOTH fail

Actual Available to SAP: 512 - 300 = 212 GB (not 512 GB)

Impact:
  ✗ SAP HANA gets OOM killed (database crashes)
  ✗ Application Server gets OOM killed (app crashes)
  ✗ Either resource contention kills both
  ✗ Users can't access system
  ✗ Data may be inconsistent (mid-transaction crashes)

Recovery:
  1. Recalculate PHYS_MEMSIZE = 212 GB (not 512!)
  2. Recalculate all EM parameters based on 212 GB
  3. Verify with HANA/DBA team for DB memory allocation
  4. Coordinate restart with DBA (both systems need restart)
  5. Apply changes to both HANA and SAP profiles
  6. Restart HANA first, then SAP
  7. Monitor both memory allocations post-restart

Lesson:
  ✓ ALWAYS coordinate with DBA/storage teams
  ✓ Use ZAMM calculator to subtract database memory
  ✓ Document memory allocation agreement (SLA)
  ✓ Regular memory audits (quarterly)
  ✓ Capacity planning when adding new systems
